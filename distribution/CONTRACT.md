# XF1 package and execution contract v1

## Ownership

The template task owns `docs/`, `runner/`, the development manifest and builder regression tests. The distribution layer owns `distribution/`, `service/` and distribution tests. A change to runner arguments, manifest schema, template ID, required paths or sidecar semantics needs coordination. Routine builds execute the same tested runner; no Excel logic is implemented in the service or bridge.

## Current approval

The deployed `/api/mcp` endpoint exposes one read-only tool, `get_current_release`, with an empty input object. A successful tool response contains the same JSON in `structuredContent` and its text content:

```json
{
  "release": {
    "schemaVersion": 1,
    "approval": "approved",
    "templateId": "xf1-base-six-sheet",
    "version": "1.2.0",
    "generation": "from-scratch",
    "runner": "runner/New-XF1Workbook.ps1",
    "manifestSha256": "<64 hex characters>",
    "package": {
      "url": "https://github.com/XF1-Advisory-Services/xf1-mcp/releases/download/v1.2.0/xf1-1.2.0.zip",
      "sha256": "<64 hex characters>",
      "bytes": 12345
    },
    "bridge": {
      "version": "1.0.0",
      "url": "https://github.com/XF1-Advisory-Services/xf1-mcp/releases/download/v1.2.0/Invoke-XF1Build.ps1",
      "sha256": "<64 hex characters>"
    },
    "requirements": {
      "os": "Windows",
      "excel": "Desktop Microsoft Excel with Formula2 support",
      "powershell": "7.0 or later"
    },
    "testedClient": "Codex",
    "otherClients": "Claude compatibility expected, not guaranteed or tested"
  },
  "instructions": "<local setup and execution instructions>"
}
```

Values above are illustrative; the actual hashes and size are generated by release preparation. Approval is selected explicitly in `service/approved-release.json` and activated only by a deliberate service deployment. It is not inferred from a development manifest, GitHub's latest release, branch contents, file timestamps or locally cached metadata. Responses set `no-store` for clients and CDNs. A null, candidate or invalid selection returns an MCP tool error and permits no build. There is no authentication, approval mutation tool, workbook upload endpoint, scheduled task or folder watcher.

## Immutable assets

The release has a stable three-part numeric version. It contains `xf1-<version>.zip` and a separately downloadable `Invoke-XF1Build.ps1`. The ZIP contains `release-manifest.json` at its root plus **only** that manifest's assets, with their relative paths retained. It contains no input workbook, output map, historical workbook map, benchmark, test output, dependency folder or server code. Accepted paths are the three known `runner/*.ps1` files and simple `docs/*.md` paths. The bridge caps compressed size at 5 MB, extracted content at 10 MB and entries at 65.

The package preserves builder manifest schema 2. Preparation copies and verifies the development assets, then assigns a fixed release version and `status: release` only in the copied manifest. This status identifies artifact form; it is **not proof of approval or publication**. The original development manifest remains unchanged. The external `release-candidate.json` has `approval: candidate` and is rejected by the production service until Vavrinec explicitly approves its exact bytes. Approval changes only the service selection, not the ZIP, copied manifest or bridge bytes. Never replace assets under a published version.

The service validates the release identity and exact versioned GitHub asset URLs. The local bridge verifies its own expected version/hash, the downloaded ZIP hash/size, copied manifest hash, package identity, required runner files and every listed asset hash. It rejects unexpected files, duplicate paths, traversal and symbolic links/junctions. OneDrive placeholder reparse points are supported. HTTPS to the explicitly configured MCP endpoint is the approval trust boundary; hashes detect mismatches but are not a separate signature authority. Public downloads are intentional.

## Local lifecycle

The bridge negotiates MCP using the 2025-06-18 Streamable HTTP protocol with the pinned MCP adapter, sends initialized notification and calls the release tool. Every invocation performs this handshake/selection; there is no offline path. It accepts JSON and SSE-framed RPC responses. The server is stateless and needs no session store.

The selected version is held in the current invocation. Downloads extract into a unique staging directory and are promoted to `package/` only after verification. A per-version exclusive lock covers validation, installation and the full Excel build. Another invocation of that version fails promptly with a retry message. Different versions occupy distinct directories. Corrupted or mismatched cache contents fail rather than being overwritten. Failed downloads clean only their own staging directory; a process killed forcibly may leave an unused `.stage-*` directory.

Only after verification does the bridge pass the documented parameters to `runner/New-XF1Workbook.ps1` in the selected package. The runner owns Excel and publishes its workbook and two sidecars as before. Package version and manifest SHA-256 in `.build.json` establish provenance; `.map.json` locates that exact version's specifications. Large workbook contents never cross the network and are not re-imported into another engine.
